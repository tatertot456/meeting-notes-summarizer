Why a Buffer Manager?

▶

Disk access is far slower than memory. The buffer manager keeps recently used disk blocks in a portion of main memory so queries hit memory instead of disk whenever possible.

The Buffer

A fixed-size pool of RAM frames. Each frame holds one disk block. The disk copy is the authoritative version until a modified frame is written back.

Buffer Manager Logic

Program requests block N. Manager checks: in buffer? Yes — return memory address, no disk access. No — evict a victim frame (write back if modified), read block N in, return address.

Every buffer block also exists on disk. A modified (dirty) buffer frame holds newer data than the disk copy. The buffer manager must write dirty frames back before evicting them — otherwise that write is lost.

Pinning and Locks

▶

A pin prevents a buffer frame from being evicted while a process is actively reading or writing it. Multiple processes may pin the same block simultaneously.

Protocol:
  pin(block 7)        // declare I need this block
  read or write data  // do the work
  unpin(block 7)      // I'm done, you may evict it

Pin count tracks concurrent pinners:
  P1 pins  → count = 1
  P2 pins  → count = 2
  P1 unpins → count = 1
  P2 unpins → count = 0  // now eligible for eviction

A block with pin count > 0 cannot be evicted. If every buffer frame is pinned, the system stalls — no new block can be read in.

Shared Lock (Read)

Any number of processes may hold a shared lock simultaneously. No process may write while a shared lock is held.

Exclusive Lock (Write)

Only one process holds it. No shared locks may coexist. All other requests wait until the exclusive lock is released.

Buffer Replacement Strategies — LRU vs MRU

▶

When no free frame exists, the buffer manager must evict a victim. The naive choice is LRU (Least Recently Used) — evict the block that was accessed longest ago. But LRU is wrong for some query patterns.

Nested loop join example: outer relation instructor, inner department. For each instructor row, all of department must be re-read. LRU evicts the department block you're about to need next — every inner access is a miss.

Buffer holds 2 department blocks. Department has 3.
Request sequence: D1 D2 D3 D1 D2 D3

LRU (evict oldest):  miss miss miss miss miss miss  → 6 reads
MRU (evict newest):  miss miss miss HIT  miss HIT   → 4 reads

The buffer manager can see the query plan and know what comes next. The optimal strategy isn't guessing from history — it's using plan knowledge. For nested loops: toss the outer (instructor) block the moment it's used; keep the inner (department) blocks as long as possible using MRU.

Journaling writes changes to a sequential log before updating data blocks. On crash, replay the log. Sequential log writes avoid random seeks — the expensive part of disk I/O.

Disk Access — Sequential vs. Random

▶

Every optimization below converts random access into sequential access. A seek (arm movement to a track) costs far more than transferring a block once there.

Sequential Access

1 seek, then N blocks transferred in a row. The arm moves once. Cost scales with transfer time, not seek time.

Random Access

N seeks for N blocks on different tracks. Each block costs a full seek. Catastrophically expensive at scale.

Read-Ahead

When block b1 is requested, the OS reads b2–b4 speculatively. The next sequential requests are cache hits with zero seeks. Pays only for sequential access patterns.

Elevator (SSTF) Scheduling

Sort pending block requests by track position. Sweep inward, then reverse. Same 6 requests: 26 tracks in arrival order vs. 7 tracks in elevator order.

Extents

Group related blocks into contiguous runs (extents). 7 scattered blocks = 7 seeks. 3 contiguous extents = 3 seeks. Fragmentation defeats this.

NVRAM Write Buffer

Writes go to non-volatile RAM first — acknowledged immediately. Disk writes are deferred and reordered into elevator order. Safe through power failure.

Flash SSDs feel seek latency less than spinning disks (20–60 µs vs 4 ms), but the principle still holds. More importantly: flash cannot overwrite a 4 KB page without erasing a full 4 MB erase block. The SSD firmware remaps pages internally to hide this, but it means sequential writes are still far cheaper than random writes on flash.

Record Layouts — Fixed and Variable Length

▶

Fixed-length records: every attribute padded to its maximum width. Record i starts at byte record_size × i — any row is found by arithmetic, no scanning needed.

instructor row: 5 + 20 + 20 + 8 = 53 bytes (fixed)
4,096-byte block: ⌊4096 / 53⌋ = 77 records, 15 bytes wasted
Record 3 starts at byte 53 × 3 = 159

No record may cross a block boundary — a split record would cost two block accesses for every read and every write.

Deletion has three options: shift all later records (expensive), move the last record into the hole (loses order), or chain deleted slots on a free list (no data movement). Free lists win because insertions outnumber deletions.

Variable-length records: for VARCHAR columns, a fixed-size header stores (offset, length) pairs for each variable attribute. The actual values are stored consecutively after the header. A null bitmap marks absent attributes.

Fixed header:  [(offset=21, len=5), (offset=26, len=10), salary=65000, bitmap=0000]
Variable data: [10101][Srinivasan][Comp. Sci.]
name starts at byte 26, runs 10 bytes — found directly from the header

The fixed-size header is the key insight. Even though values vary in length, the header is the same size for every row. Code that reads the header always knows where to find each field's offset/length pair — no scanning within the record.

Slotted-Page Structure

▶

A block holding variable-length records needs a way to find each record and keep free space contiguous. The slotted-page structure solves both.

Block layout (4,096 bytes):
[block header | slot directory | ... free space ... | record 3 | record 2 | record 1]
                                                      ← records fill from the END

Slot directory (inside header):
  n = 3          // number of records
  slot 1: (4051, 45)   // offset 4051, length 45 bytes
  slot 2: (4014, 37)
  slot 3: (3974, 40)
  slot 4: (-1)         // deleted — slot entry is -1

External pointers reference a slot number, never a byte offset. This lets the block compact records (slide them together to merge free space) without invalidating any outside references — the slot entry is updated, the slot number stays the same.

Indirection through slot numbers is what makes compaction possible. If external pointers pointed directly to byte offsets, moving any record would break every pointer to it. Slot indirection adds one level of lookup but enables free space consolidation — worth the cost.

Storing Large Objects (BLOBs)

▶

Attributes like photos (4 MB) or lecture videos (2.1 GB) far exceed a block's capacity. The row stores a small pointer; the object lives elsewhere.

Inside the Database

Stored as a B+-tree file organization. Any byte range can be read or written directly. Constraints, authorization, and backup all apply. But database dumps grow enormously.

In the File System

Row stores a path name. Backups stay small. But SQL authorization cannot reach the file — a deleted row leaves a dangling pointer to an orphaned file.

File Organization — Five Ways to Store a Relation

▶
OrganizationWhere a Record GoesBest For
HeapAnywhere there is free space — no orderFast inserts; full scans
SequentialIn search-key order, chained by pointersReading rows in sorted order
Multitable ClusteringBeside related rows of another relationJoins on the cluster key
B+-tree (Ch. 14)Kept in key order by the tree itselfOrdered access under heavy updates
Hashing (Ch. 14)In the block the hash function namesSingle key equality lookups

Heap: uses a two-level free-space map. Each entry is a fraction-free score (0–7). A second level stores the max of every four entries so large blocks can be found without scanning the whole map.

Sequential: new records whose block is full go to an overflow block, chained to maintain sorted order. Physical order drifts as inserts accumulate. Periodic reorganization is expensive — this is why B+-tree file organization replaced it.

Multitable clustering: co-locates department and instructor rows so a natural join on dept_name needs one block read instead of two. Tradeoff: SELECT * FROM department now touches more blocks because instructor rows are interleaved.

Table partitioning: splits one relation into smaller pieces by a partition key (e.g., year). A query with a matching WHERE clause touches only the relevant partition. Without the condition, every partition is scanned.

No single file organization wins everything. Heap is best for bulk inserts, sequential for range scans, clustering for joins, hashing for point lookups. Real systems let you choose per-table, and the query optimizer picks the access path at query time.
