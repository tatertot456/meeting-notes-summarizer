The Concurrency Crux — Two Workers, One Counter

▶

Last time: the OS virtualizes the CPU (four loops, one processor) and memory (same address, different contents). Now: what happens when two virtual CPUs touch the same data at the same time?

// threads.v0.c — OSTEP Fig. 2.5
volatile int counter = 0;   // shared between both threads
int loops;

void *worker(void *arg) {
    for (int i = 0; i < loops; i++) {
        counter++;           // looks like one operation — it isn't
    }
    pthread_exit(NULL);
}

int main(int argc, char *argv[]) {
    loops = atoi(argv[1]);
    pthread_t p1, p2;
    printf("Initial value : %d\n", counter);
    Pthread_create(&p1, NULL, worker, NULL);  // thread 1
    Pthread_create(&p2, NULL, worker, NULL);  // thread 2
    Pthread_join(p1, NULL);   // wait for both
    Pthread_join(p2, NULL);
    printf("Final value   : %d\n", counter);
}

Each thread adds 1 to counter for loops iterations. Two threads × 1000 loops = expected final value of 2000. What actually happens:

loops valueResultWhy
1,000Always 2000 ✓Thread 1 finishes before thread 2 is even created — no overlap
10,000Sometimes right, usually wrongOccasional overlap — race shows up intermittently
100,000+Always wrong, different each runHeavy overlap — lost updates almost every iteration

There is not a single random number in this program. Same binary, same input — different wrong answers every run. The wrong answers sit between one thread's total and two threads' total, and get closer to one thread's total as loop count grows. That's the clue.

What Pthread_create Builds — Process vs. Thread

▶

Process

An address space plus at least one thread. Owns: code, globals, heap, open files, pid. All threads inside a process SHARE these.

Thread

A program counter, registers, and a stack. Nothing else. Everything else is shared with sibling threads inside the same process.

Pthread_create

Creates one more thread in the current process, starting at the given function. The new thread shares all memory — including counter.

Pthread_join

main waits until the specified thread finishes before continuing. Without join, main might print before workers are done.

one process = one address space, shared by all threads:
  code:   worker(), main()
  globals: counter = 0, loops
  heap:   (malloc'd memory)
  open files, pid, ...

private to each thread:
  main thread:   PC · registers · stack  (waiting in join)
  thread p1:     own PC · own registers · own stack  → worker()
  thread p2:     own PC · own registers · own stack  → worker()

both p1 and p2 point at the SAME counter in the shared globals

On a multi-core machine, p1 and p2 literally run at the same instant on different cores — both reading and writing the same memory word. This is not a hypothetical. Creating the second thread takes tens of microseconds — that's why 1000 loops is fine (thread 1 finishes in that time) but 100,000 loops causes heavy overlap.

Why It Fails — counter++ Is Three Instructions

▶

One C statement compiles to three machine instructions. Nothing ties them together:

// counter++ as compiled (ARM64):
ldr  w0, [x0]       // 1. LOAD counter from memory into a register
add  w1, w0, #1     // 2. ADD one, staying in the register
str  w1, [x0]       // 3. STORE it back to memory

// Between ANY two of these instructions,
// the other core can do anything to the same memory word.

The lost update scenario — two cores, one counter starting at 50:

time →
core 0 · thread A    core 1 · thread B    memory · counter
ldr → 50                                  50
add → 51             ldr → 50             50    // B loads BEFORE A stored!
str  51              add → 51             51
                     str  51              51    ✗ lost one increment

// A and B both read 50, both compute 51, both store 51.
// Two increments happened. Counter grew by ONE.

On a single core, the same bug exists — a timer interrupt can land between the load and the store, switching to another thread. On two cores, no interrupt is needed: the collision happens on almost every iteration. That's why the wrong answers approach "one thread's total" — the second thread's work is almost entirely lost.

This is called a race condition. The three instructions form a critical section — code that must execute atomically (as if it were one indivisible operation) to be correct. The goal of concurrency primitives (locks, atomics) is to enforce atomicity over critical sections.

The Fix — Mutex Lock

▶ 
// threads.v1.c — the locked version (changed lines marked)
pthread_mutex_t m;                    // ONE lock, guarding counter

void *worker(void *arg) {
    for (int i = 0; i < loops; i++) {
        Pthread_mutex_lock(&m);       // acquire lock — or WAIT
        counter++;                    // critical section: one thread at a time
        Pthread_mutex_unlock(&m);     // release lock — wake a waiter
    }
    pthread_exit(NULL);
}

int main(...) {
    Pthread_mutex_init(&m, NULL);     // initialize before any thread uses it
    // ... same as before ...
}

A mutex (mutual exclusion) has two states: free, or held by exactly one thread. If thread B arrives at lock() while A holds it, B waits until A calls unlock(). The three load-add-store instructions can no longer be split by another thread.

// threads_locked — correct at every size, every run:
prompt> ./threads_locked 100000
Final value   : 200000
prompt> ./threads_locked 1000000
Final value   : 2000000  ✓ every single time

What it costs:

Version100M loopsResult
No lock (broken)0.25 s · 195% CPUWrong (~101M)
With lock (correct)1.96 s · 175% CPU200,000,000 ✓

8× slower. 0.65s of that is kernel time — the waiting thread is put to sleep and woken at unlock. 175% CPU (not 195%) means one core was partly idle while its thread waited. Correctness has a price. Weeks 8–10 ask: how to pay less. (Hint: atomic instructions — LOCK XADD on x86 — do the whole read-modify-write as one hardware operation, no kernel involved.)

The lock didn't stop the two threads from running simultaneously — it only moved the boundary to between increments rather than inside one. A trace of 200,000 increments showed 86,581 thread switches — heavy interleaving, but always correct.

Persistence — Memory Forgets, Disks Don't

▶

DRAM is volatile — power off, everything gone. Files must outlive the process, the crash, and the power cut. Three system calls hand that job to the file system:

// io.c — OSTEP Fig. 2.6
int main(int argc, char *argv[]) {
    // 1. open: a name becomes a file descriptor (small integer)
    int fd = open("/tmp/file", O_WRONLY|O_CREAT|O_TRUNC, S_IRWXU);
    assert(fd >= 0);

    // 2. write: 13 bytes from RAM into the file
    int rc = write(fd, "hello world\n", 13);  // 11 + space + \n + \0 = 13
    assert(rc == 13);

    // 3. close: kernel forgets the descriptor; file persists
    close(fd);
    return 0;
}

What write() sets in motion:

  • write() copies bytes into the kernel's page cache (RAM) and returns immediately — no disk involved yet
  • The page is marked dirty — written but not yet on disk
  • Linux writes dirty pages to disk within ~30 seconds on its own schedule
  • Power cut inside that 30-second window = bytes are gone, even though write() returned success

What the file system stores (inode structure):

directory /tmp
  "file" → inode 372

inode 372:
  size: 13 bytes · owner · permissions · timestamps
  block pointer → data block (4096 bytes on disk)
    [h][e][l][l][o][ ][w][o][r][l][d][\n][\0][...unused...]

// A name → a number → the bytes.
// Name and bytes are kept in DIFFERENT places on disk.

13 bytes cost one 4 KB disk block. Small files waste most of it — disk space is handed out in 4 KB chunks. The inode is the file's identity: size, owner, permissions, times, and where the bytes are. The directory just maps the name to the inode number. Weeks 12–13 open up the full inode and block map.

The Page Cache — The 30-Second Window

▶ 
// Ubuntu: measure how much written data sits in RAM, not yet on disk
$ grep Dirty /proc/meminfo
Dirty:        144 kB                    // baseline

// Write 200 MB:
$ dd if=/dev/zero of=big.bin bs=1M count=200

$ grep Dirty /proc/meminfo
Dirty:     204828 kB                    // 200 MB waiting in RAM!

// Force it to disk:
$ time sync
real    0m0.082s

$ grep Dirty /proc/meminfo
Dirty:          0 kB                    // all flushed

$ cat /proc/sys/vm/dirty_expire_centisecs
3000                                    // 30 seconds (3000 centiseconds)

Why the Cache Exists

RAM absorbs writes instantly. Disk writes are batched for efficiency. dd finished in 0.03s — 200 MB written at memory speed, not disk speed.

The Risk

Power cut inside the 30-second window = bytes the program was told were written are gone. write() returned 13, success — but the disk had nothing yet.

The page cache is the same pattern as the SSD's own DRAM cache — "complete" means "in my RAM" at every level. The question "where are the bytes?" is the key question for anyone building storage-sensitive systems.

fsync — Closing the Window

▶

fsync(fd) blocks until the disk has the data — it closes the 30-second window, but at a price:

// Ubuntu, ext4 on SSD:
$ ./fsync_test 1000 0         // no fsync
1000 writes, fsync=0 : 0.000 s  (0.2 µs per write)

$ ./fsync_test 1000 1         // fsync after every write
1000 writes, fsync=1 : 1.638 s  (1638 µs per write)

// 0.2 µs vs 1,638 µs — about 4,000× slower per write

Every database pays this on every commit. The gap between 0.2 µs and 1,638 µs is why database performance is so hard — and why techniques like write-ahead logging (WAL) and group commit exist: batch many writes into one fsync call instead of one per transaction. macOS note: fsync() only reaches the drive's own cache; use F_FULLFSYNC for the real guarantee.

ApproachSpeedDurabilityUse When
write() alone~0.2 µsMaybe — 30s windowData you can afford to lose (logs, caches)
write() + fsync()~1,638 µsYes — disk has itFinancial records, database commits
WAL + group commitMiddle groundYes — batchedReal databases — one fsync per batch of transactions
Replication before ackNetwork latencyYes — survives single failureDistributed systems (Kafka acks=all, Raft majority)

OS Design Goals & The Full Picture

▶

Abstraction

Find the right ideas (process, address space, file) so programs are easy to write on top. The right abstraction hides complexity without hiding what matters.

Performance

Virtualization must cost little — minimize overhead in time and space. Every mechanism has a cost; every week's designs are measured against it.

Protection & Isolation

A buggy or malicious program must not harm others — or the OS itself. Process A writing past its array cannot touch process B. Ever.

Reliability

The OS must run non-stop. When the kernel fails, everything fails. This is why kernel code is held to a higher standard than application code.

Vocabulary you now own:

  • Race condition — outcome depends on the timing of events (bad)
  • Critical section — code that must execute atomically
  • Atomicity — appears to happen as one indivisible operation
  • Mutex — mutual exclusion lock: only one thread inside the critical section at a time
  • File descriptor — small integer the kernel uses to track an open file
  • Page cache — kernel's RAM buffer for disk writes; dirty = written but not yet on disk
  • fsync — forces dirty pages to disk before returning

The three pieces, complete:
