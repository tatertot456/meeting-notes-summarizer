What Is a Process?

▶

A program is a file on disk. A process is that program running. To fully describe a process, list everything it can touch while it runs:

1. Address Space (Memory)

Stack (locals, argv), heap (malloc), static data (globals), code (text). Each region sits at a different virtual address. One program can be many processes — four copies of cpu.c are four processes with four separate address spaces.

2. Registers

Program counter (PC), stack pointer (SP), ~30 general-purpose registers. Save these 32 numbers and the process is frozen. Load them back and it continues as if nothing happened. This is the whole mechanism of context switching.

3. Open Files (I/O State)

Per-process file descriptor table. Every process is born with 0 (stdin), 1 (stdout), 2 (stderr) already open. Redirection is just swapping entries in this table.

struct proc in xv6

Every process is one C struct. Key fields: state, pid, parent, pagetable (memory map), trapframe (saved user registers), context (saved kernel registers), ofile[] (open files), cwd (current directory). xv6 keeps 64 of these in a global array proc[NPROC].

To pause a process the OS only needs to keep these three things. To run many processes it only needs to keep them separate. One program can be many processes at once — last week's four copies of cpu.c were four processes, four separate copies of this picture.

The address space is not one contiguous block:

0x7fffffffffff   top of user space (128 TiB)
[stack]  ~144 KB
  local variables, argv, envp live here

      gap: ~42 TB of nothing (libc mapped near stack)

[heap]  ~132 KB
  malloc'd memory grows upward from here

      gap: ~917 MB of nothing

data  rw-p   4 KB   (globals)
code  r-xp   4 KB   (program text — readable + executable, NOT writable)
ELF header   4 KB
0x0   nothing — NULL pointer faults here

Every boundary ends in 000 — the unit is 4 KB pages. The gaps are real and enormous. The "strip" diagram is right about ORDER, not spacing. This is /proc/PID/maps on Ubuntu.

Birth of a process (exec path):

  • Load code and static data from the ELF file into memory (lazily — pages brought in on first touch)
  • Allocate the stack, fill in argc and argv
  • Allocate a small heap for malloc
  • File descriptors 0, 1, 2 are inherited — printf works from line one
  • Jump to main() — set PC, switch to user mode

Linux merges RUNNING and RUNNABLE into one letter R — only /proc/PID/stat plus a CPU column can distinguish them. Linux also adds T (stopped by signal, Ctrl-Z) which xv6 lacks. ZOMBIE means the same thing on both.

Time sharing — the answer to the first crux: run one process for a while, then another. The cost is honest — each runs slower than alone. The alternative is space sharing (disk blocks, memory pages). This week is entirely mechanism. Policy (which process, how long) is weeks 6–7.

fork() — One Call, Two Returns

▶ 
// p1.c — the complete fork pattern
int main(int argc, char *argv[]) {
    printf("hello world (pid:%d)\n", getpid());
    int rc = fork();
    if (rc < 0) {
        fprintf(stderr, "fork failed\n");  // always check
        exit(1);
    } else if (rc == 0) {
        // I am the child — fork() returned 0
        printf("hello, I am child (pid:%d)\n", getpid());
    } else {
        // I am the parent — rc is my child's pid
        printf("hello, I am parent of %d (pid:%d)\n", rc, getpid());
    }
    return 0;
}

What fork() does: asks the kernel to copy the calling process. The child does NOT start at main() — it wakes up INSIDE fork(), at the same instruction as the parent, and continues from there. That's why "hello world" prints once.

Child gets rc = 0

"You are the copy." The child needs no pid — it has getpid() for itself and getppid() for its parent.

Parent gets rc = child's pid

The only handle the parent has on the child. Used by wait(), kill(), and restart loops.

What's copied

Memory (every page), registers, open file table. Shared open files (not copied) — both child and parent write to the same terminal. This is why redirection and pipes work.

What differs

pid, parent pointer, and one register: a0 (the return value). The kernel sets a0=0 in the child's trapframe. That one line in proc.c is why fork() returns 0 in the child.

Who runs first after fork() is nondeterministic. The scheduler picks. In 19/20 runs the parent went first; once the child did. Same program, two different outputs. This is the same nondeterminism as last week's threads bug — but with processes. To force an order, use wait().

Surprise — fork copies printf's buffer: send output to a file with > and "hello world" appears twice. printf buffers output in memory; when output is a file it flushes at exit, not at newlines. fork() copied the buffer. Two processes, two flushes.

Why two calls (fork + exec) instead of one? The gap between fork() and exec() lets the child rearrange its world — close a file descriptor, open a file, set up a pipe — BEFORE the new program starts. Windows CreateProcess() does it in one call but needs 10 parameters to pass all that context.

xv6 fork() in 8 moves (kfork in proc.c):

  • allocproc() — find first UNUSED slot in proc[64]
  • uvmcopy() — copy every page of parent's memory
  • Copy the trapframe (all 31 saved user registers + PC)
  • Set a0 = 0 in the child's trapframe (the return value)
  • filedup() — increment refcount on shared open files
  • Set child.parent = parent (the family tree)
  • Set child.state = RUNNABLE
  • Return child's pid to the parent

wait() and Zombies

▶ 
// p2.c — wait() guarantees the child prints first
int rc = fork();
if (rc == 0) {
    printf("hello, I am child (pid:%d)\n", getpid());
} else {
    int rc_wait = wait(NULL);  // block until a child exits
    printf("hello, I am parent of %d (rc_wait:%d)\n", rc, rc_wait);
}

wait(NULL) blocks the parent until one child has exited. Returns that child's pid. Through its argument it can also return the child's exit status. While blocked the parent is in SLEEPING state — costs zero CPU.

Why the order is now certain: either the child ran first anyway, or the parent ran first and immediately blocked in wait() until the child finished. Both roads lead to the child printing first.

The Zombie:

  • Child calls exit() → closes files, parks exit status in struct proc, state becomes ZOMBIE, never runs again
  • Kernel cannot free the slot — it holds a status nobody has collected yet. A dying process also can't free itself because it's still running on its own kernel stack.
  • Parent calls wait() → finds the ZOMBIE child, copies exit status out, frees everything, returns child's pid. Z disappears from ps.

Orphans go to init (pid 1) when a parent dies first. init's whole job is to call wait() in a loop. That's why killing a zombie's parent makes the zombie vanish instantly. Rule for your own code: every fork() needs a matching wait() somewhere — or a SIGCHLD handler that does it. A server that forks per request and never waits leaks one process slot per request. xv6 has 64; Linux has 32,768 pids by default. Eventually fork() returns -1 while the machine does nothing.

exec() — Become a Different Program

▶ 
// p3.c — fork a child, exec wc inside it
if (fork() == 0) {
    char *myargs[] = {"wc", "p3.c", NULL};
    execvp(myargs[0], myargs);   // replace me with wc
    printf("never printed");     // only runs if exec FAILED
}
wait(NULL);

// Output:
// hello world (pid:1467)
// hello, I am child (pid:1468)
// 27 122 911 p3.c              ← wc ran here, same pid 1468
// hello, I am parent of 1468

What exec() does NOT change: pid, parent, open file descriptors

What exec() DOES change: memory (new code, data, stack, heap), program counter (set to new program's entry point)

A successful exec() never returns — the code it would return to is gone. The line after execvp() only runs if exec failed.

exec() in 8 kernel moves:

  • namei(path) — find the file
  • Read ELF header
  • Build a new empty page table
  • Load code and data segments
  • Allocate a fresh user stack
  • Copy argv strings onto the new stack
  • Switch to the new page table, set PC to entry point
  • Free the OLD memory last — so a failed exec can still return -1

fork() creates a new process with the same program. exec() gives the same process a new program. Neither alone can start a program — it takes both. The gap between them is the entire reason Unix has two calls: close a file, open another, rearrange the world, THEN become the new program.

Redirection — the gap in action:

// The shell running: wc p4.c > out.txt
if (fork() == 0) {
    close(1);                                          // free slot 1
    open("out.txt", O_CREAT|O_WRONLY|O_TRUNC, 0644); // lands in slot 1
    execvp("wc", args);                                // wc inherits the table
}
// open() always returns the LOWEST free descriptor.
// Close 1, next open() gets 1. exec() keeps the table.
// wc writes to fd 1 as it always does — never knows it's a file.

The Shell — A Loop of fork, exec, wait

▶ 
// The shell's inner loop (simplified):
while (read_line(buf)) {
    if (is_cd(buf)) {
        chdir(buf+3);      // cd MUST run in the parent
    } else {
        if (fork() == 0)
            exec(cmd, args);   // child becomes the program
        wait(NULL);            // parent blocks until done
    }
}  // print next prompt

Why cd is special: if the shell forked a child to run chdir(), the child's directory would change and then the child would exit — the shell itself would be where it was. cd must run in the parent process.

Why the prompt returns only when the command is done: the parent is blocked in wait() the entire time the child runs.

A pipe is redirection done twice:

// ls -l | wc -l implemented by hand (p5.c):
int p[2];
pipe(p);              // p[0]=read end, p[1]=write end

if (fork() == 0) {    // child 1: ls -l
    close(1); dup(p[1]);          // stdout → pipe write end
    close(p[0]); close(p[1]);
    execlp("ls", "ls", "-l", NULL);
}
if (fork() == 0) {    // child 2: wc -l
    close(0); dup(p[0]);          // stdin → pipe read end
    close(p[0]); close(p[1]);
    execlp("wc", "wc", "-l", NULL);
}
close(p[0]); close(p[1]);         // parent closes both ends
wait(NULL); wait(NULL);

// ls writes to fd 1 — doesn't know it's a pipe
// wc reads from fd 0 — doesn't know either
// wc sees EOF when every write end is closed

The kernel pipe is a 64 KB byte queue in memory — no file on disk, no temporary storage. If the queue fills the writer blocks; if it empties the reader blocks. Neither ls nor wc changed a single line. The shell rearranged the children's worlds, then became the programs.

Limited Direct Execution — Staying in Control

▶

The OS wants two things simultaneously that fight each other: run the program directly on the CPU (fast) and never lose the ability to stop it or forbid dangerous actions (control). The answer is limited direct execution.

Problem 1 — Restricted Operations: Two CPU Modes

User Mode

Restricted — no device access, no other process's memory, no privileged instructions. All application code runs here. A privileged instruction in user mode raises a hardware exception — the CPU refuses it.

Kernel Mode

Unrestricted — touch any device, any memory, any register. The difference is one bit in a CPU control register, checked by hardware on EVERY instruction.

The trap (ecall on RISC-V) — the one legal way up:

  • A system call is a trap: one instruction that (1) switches to kernel mode and (2) jumps to a fixed address the KERNEL chose in advance
  • The program cannot pick where it lands — only says "I want service number N"
  • The kernel installs the trap handler address at boot using a privileged instruction (w_stvec). User code cannot change this.
  • A program cannot name a kernel address to jump to — impossible by construction

A system call — 6 stations:

1. Program:  put call number in a7 register, execute ecall
2. Hardware: save user PC, switch to kernel mode, jump to handler
3. Kernel:   save all 31 user registers into trapframe, switch to kernel stack
4. Kernel:   look up number in syscall table, call handler, result → saved a0
5. Kernel:   restore user registers from trapframe (a0 = result)
6. Hardware: sret — drop to user mode, jump to saved PC (instruction after ecall)

Cost on Ubuntu: ~100 ns per crossing — about 85× a plain function call.
This is why programs buffer output instead of calling write() per byte.

Protection is enforced by silicon, not by the OS asking nicely. What could you do if you could install your own trap table? You could point "system call" at your own code running in kernel mode — you'd own the machine. That's exactly why setting the trap address is itself a privileged operation.

Timer Interrupts and Context Switches

▶

Problem 2 — Taking the CPU back:

Cooperative approach: trust programs to yield via system calls. Fatal flaw:

while(1);   // no system call, no illegal instruction, ever
            // In a cooperative world the OS never runs again

The only answer — the hardware timer:

  • At boot (privileged): install a timer handler + start hardware timer: "interrupt me every few milliseconds"
  • Starting/stopping the timer is privileged — a user program cannot turn it off
  • Every tick: hardware saves the running program's state and jumps into the kernel handler — exactly like a trap, but nobody asked
  • Now the OS is running and can decide: keep this process or switch

Trap vs. Interrupt: a trap is the program calling the kernel. An interrupt is the hardware calling the kernel. Same machinery, opposite direction. The infinite loop is now powerless — the clock ticks, the interrupt fires, the OS runs. Control is guaranteed by physics, not politeness.

The context switch — saving A, loading B:

// swtch.S in xv6 — the ENTIRE context switch (29 instructions):
swtch(old, new):
    // Save 14 callee-saved registers into old->context
    sd ra, 0(a0); sd sp, 8(a0); sd s0, 16(a0) ... sd s11, 104(a0)
    // Load 14 registers from new->context
    ld ra, 0(a1); ld sp, 8(a1); ld s0, 16(a1) ... ld s11, 104(a1)
    ret  // follows new's saved return address — returns into B's code

// Loading new's stack pointer is the point of no return.
// After it we are on B's kernel stack. ret lands in B's kernel code.
// swtch was called by A and returns into B.

Two saves per hand-off, not one:

  • On the timer interrupt: hardware saves A's user registers to A's kernel stack (trapframe)
  • OS saves A's kernel registers to A's struct context
  • OS loads B's context, switches to B's kernel stack
  • When B returns to user mode its trapframe is restored

xv6 always switches through a per-CPU scheduler thread — A → scheduler → B. Never A directly to B. Two swtch() calls per hand-off. This keeps all switching logic in one place.

These three numbers explain a huge amount of systems design. Why programs buffer output: syscalls cost 100 ns each. Why servers use thread pools instead of fork-per-request: context switches cost 1 µs. Why Linux added io_uring: submit many I/Os per trap instead of one syscall each. Every crossing costs — and these costs are why.

Loose end — interrupts during traps: a timer interrupt can fire while the kernel is mid-system-call. Now two activities are inside the kernel touching the same data — the same race as last week's counter bug, one level down. xv6's solution: disable interrupts during certain operations, protect kernel data with spinlocks (acquire() turns interrupts off on that CPU until release()). This is weeks 8–10. struct proc has a spinlock on its very first line — now you know why.
