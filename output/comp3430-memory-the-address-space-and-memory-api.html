How Memory Got Complicated

▶

Early systems ran one program at a time — no abstraction needed because there was nothing to protect. Multiprogramming changed that.

The Early Days

One program at a time. OS sits at physical 0, the program gets the rest. No protection needed — no one else is in memory.

Multiprogramming

Several programs resident at once so the CPU is never idle. Machines cost millions and had to be shared. Now a bad pointer in process A can corrupt process B or the OS itself.

The obvious fix, and why it fails: save the entire program's memory to disk on each context switch, load the next program in. This is correct but catastrophically slow — copying gigabytes of memory to disk many times per second is not feasible. So processes must stay in memory together, which forces three requirements:

  • Efficiency — processes must share memory simultaneously
  • Protection — sharing makes isolation mandatory, checked on every access
  • Abstraction — protection must stay invisible to the programmer

The Address Space

▶

The OS gives each process the illusion of a private address space. Three regions, three purposes:

Code (Text)

Static — doesn't grow. Placed at the lowest addresses where nothing needs to expand into it.

Heap

Holds malloc'd memory. Grows toward higher addresses (downward in the diagram). Lives just above the code segment.

Stack

Holds locals, function arguments, and return addresses. Grows toward lower addresses (upward in the diagram). Lives at the top of the address space.

Why Opposite Ends?

Heap and stack sit at opposite ends of the address space so both can grow into the free region between them without immediately colliding.

This layout is a convention, not a law. In week 8, when one process has multiple threads, each thread needs its own stack — and the single-stack picture completely breaks down.

The crux of memory virtualization: how can the OS give many running processes each a private, potentially large address space while they all share one physical memory? The answer is that every address a program ever sees is virtual. When the process loads address 0, the hardware quietly redirects that load to somewhere else in physical RAM — and the process cannot tell.

Every Pointer Is Virtual — The va.c Demo

▶ 
// va.c — prints addresses from all three regions
#include <stdio.h>
#include <stdlib.h>
int main(int argc, char *argv[]) {
    printf("location of code : %p\n", main);        // code region
    printf("location of heap : %p\n", malloc(100e6)); // 100 MB on heap
    int x = 3;
    printf("location of stack: %p\n", &x);          // stack
    return x;
}

// Ubuntu 24.04 output:
location of code : 0x55c5b5585189
location of heap : 0x7f9e470a1010
location of stack: 0x7ffcfb971f04

Three surprises in the output:

  • Order matches the picture — code lowest, heap middle, stack highest
  • Stack address is ~140 TB — the machine has 8 GB of RAM. Virtual addresses are not RAM locations.
  • 100 MB returned instantly — the OS promised the memory, it didn't deliver it. Pages arrive only when touched (demand paging, week 7).

The heap address (0x7f9e...) appears near the stack rather than just above the code. A 100 MB request is too large for the ordinary heap — the kernel fulfills it with mmap, creating a fresh region near the top of the address space. strace catches this happening in real time.

// strace reveals what malloc actually does:
$ strace -e trace=brk,mmap ./va
brk(NULL)                    = 0x55c356dff000  // where does heap end?
brk(0x55c356e20000)          = 0x55c356e20000  // expand heap ~132 KB
mmap(NULL, 100003840, ...)   = 0x7f547f4a1000  // 100 MB via mmap, not brk
location of heap : 0x7f547f4a1010              // 16 bytes inside mmap region

The two brk calls show the allocator buying a pool of ~132 KB to retail in small pieces. The 100 MB request bypasses that entirely and gets its own mmap region. Most small mallocs never reach the kernel at all.

ASLR — Address Space Layout Randomization

▶

Run the same binary three times without recompiling — every address changes:

$ ./va
code: 0x55c5b5585189   heap: 0x7f9e470a1010   stack: 0x7ffcfb971f04
$ ./va
code: 0x561b7fd64189   heap: 0x7f400b0a1010   stack: 0x7ffe8c533474
$ ./va
code: 0x55901a077189   heap: 0x7f8006aa1010   stack: 0x7ffede346384

// Turn it off with setarch -R:
$ setarch x86_64 -R ./va
code: 0x555555555189   heap: 0x7ffff1ca1010   stack: 0x7fffffffac24
$ setarch x86_64 -R ./va
code: 0x555555555189   heap: 0x7ffff1ca1010   stack: 0x7fffffffac24
// identical every time

ASLR is one of the cheapest exploit defenses ever deployed. An attacker who wants to hijack a program needs to know where things are in memory. Reshuffling the layout on every run makes addresses learned from a previous run worthless. It raises the cost of exploitation but doesn't end it: leaking one pointer tells an attacker where an entire region landed.

Practical consequence this week: gdb disables ASLR by default so breakpoints stay put. That's why addresses look stable in the debugger but change outside it. If a classmate's addresses don't match yours, nothing is broken.

The Memory API — malloc, free, and the Rules

▶

Four calls make up most of the memory API:

CallWhat It DoesKey Rule
malloc(size)Allocates size bytes on the heap, returns a void pointerAlways check the return value for NULL
free(ptr)Returns the block pointed to by ptr back to the allocatorMust pass the original pointer returned by malloc — never an offset
calloc(n, size)Allocates n*size bytes and zeroes themUse when you need guaranteed zero initialization
realloc(ptr, size)Resizes an existing allocation, may move itAlways reassign the return value — old pointer may be invalid after call

malloc is NOT a system call. It appears in no kernel syscall table — not Linux's 350+, not xv6's 22. It lives entirely in user space as a C library function. The library manages a pool of memory, carving out your requests without ever crossing into the kernel. Only when the pool runs dry does it call brk or mmap to get more territory from the OS.

// malloc's relationship to the kernel:
your program:    malloc(24)  free(p)
                      ↕
C library (libc): manages a pool in user space — fast, no trap
                      ↕ only when pool is empty
kernel:           brk/sbrk (extend heap)
                  mmap (create new region for large requests)

A trap into the kernel costs ~100 ns. Carving a block from an existing pool costs nanoseconds. The library buys territory in large pieces rarely, then retails it in small pieces often — most malloc calls in your program never reach the kernel.

Never call brk yourself. It is the allocator's private lever. Moving it behind the allocator's back corrupts its bookkeeping entirely.

Memory Bugs — The Classic Six

▶
#BugCode PatternSymptom
1Forget to allocatechar *s; strcpy(s, src);Segfault or silent corruption — s is uninitialized
2Not enough spacemalloc(strlen(src)) instead of strlen(src)+1Off-by-one overwrites the null terminator
3Uninitialized readint *x = malloc(sizeof(int)); return *x;Returns garbage; xv6 fills pages with 0x05 to make this obvious
4Buffer overflowstrcpy(buf, "way too long");Overwrites adjacent memory; valgrind catches heap version, misses stack version
5Use after freefree(x); *x = 7;Writes into memory now owned by someone else; one of the most exploited bug classes in browsers and kernels
6Double freefree(x); free(x);Corrupts allocator's free list; undefined behavior

Use-after-free is not a student mistake. It is one of the most exploited vulnerability classes in production software and a primary reason the industry is now seriously considering Rust for systems programming.

Tools and their blind spots:

Valgrind

Runs the finished binary without recompiling. 20–50x slowdown. Catches heap overflows and use-after-free precisely. Misses stack/global overflows entirely — it cannot know where one stack variable ends and the next begins.

AddressSanitizer (ASan)

Built into the compiler (-fsanitize=address). 2–4x slowdown. Catches stack, heap, and global buffer overflows. Misses uninitialized reads (that's MemorySanitizer). Must rebuild — cannot use on a finished binary.

What malloc Actually Gives You — Demand Paging Preview

▶

A program allocates 1 GB and we watch VmSize (promised) vs. VmRSS (actually delivered in RAM):

MomentVmSize (promised)VmRSS (in RAM)
At startup2,700 kB1,432 kB
After malloc(1 GB)1,051,280 kB1,760 kB
After touching all of it1,051,280 kB1,050,336 kB

The middle row is the entire point. The process was promised a gigabyte and given 328 kB. Memory arrives page by page only as the program touches it — this is demand paging (week 7). This is why a machine can run programs whose promises add up to far more RAM than it has, why "out of memory" arrives long after the allocation that caused it, and why the Linux OOM killer exists: the kernel wrote cheques on Tuesday that it cannot cash on Friday.

xv6 kalloc — The Kernel's Allocator in Four Lines

▶

xv6's kernel allocator (kalloc.c) manages a free list of 4096-byte pages. The entire data structure is four lines:

// kernel/kalloc.c lines 17-24
struct run {
    struct run *next;   // pointer to next free page
};

struct {
    struct spinlock lock;   // ignore until week 8
    struct run *freelist;   // head of the free list
} kmem;

The trick: a free page IS the list node. The next pointer is written into the first 8 bytes of the page itself. Bookkeeping for every free page in the machine costs zero extra memory — it lives inside memory that nobody is using anyway.

// kernel/kalloc.c lines 68-82 — handing out a page
void *kalloc(void) {
    struct run *r;
    acquire(&kmem.lock);
    r = kmem.freelist;         // take the head
    if (r)
        kmem.freelist = r->next;  // head moves on
    release(&kmem.lock);

    if (r)
        memset((char *)r, 5, PGSIZE);  // fill with junk (byte 0x05)
    return (void *)r;
}

Three things happening:

  • Lines 74 and 76 are the entire allocation — no search, no size tracking, no fragmentation. Constant time regardless of how much memory is free.
  • memset fills the page with 0x05 on purpose — kfree() fills with 0x01. If your code reads uninitialized memory, you see obvious garbage instead of a plausible zero.
  • If you see 0x05050505 in a debugger — you are reading memory you were given but never initialized. The kernel put that there so the bug would be visible.

Every page is exactly 4096 bytes — nothing to record, nothing to search, nothing to split or merge. This simplicity is why the kernel allocator is O(1). User-space allocators like glibc's malloc handle variable-size requests and must track sizes, merge freed blocks, and manage fragmentation — a much harder problem on top of the pages kalloc provides.
