The Hardware Underneath

▶

Before understanding what an OS does, you need a mental model of the hardware it manages.

What a running program is, to hardware — the CPU:

  • A program counter (PC) — the address of the next instruction to execute
  • ~32 registers holding the values actively in use right now
  • That's nearly all the visible state of a running program
  • Save those registers, load another program's, and you have switched programs — this is the essence of context switching

Memory is a hierarchy — everything is slow except registers:

LevelApproximate Latency
Registers~0.3 ns
L1 / L2 Cache1 to 10 ns
DRAM (main memory)~100 ns
SSD~100 µs
Hard Disk~10 ms

Registers to disk is a factor of roughly 30 million. This gap drives nearly every OS design decision about caching and I/O.

Two privilege modes — the one bit that makes an OS possible:

User Mode

Cannot touch hardware devices or access another program's memory. All normal application code runs here. The OS enforces this boundary.

Kernel Mode

Can do anything — access all hardware, all memory. The difference is one bit in a CPU control register. A trap instruction is the only door between modes.

Even the hardware lies. Modern CPUs overlap and reorder instructions internally, then preserve the illusion that they ran one at a time, in order. The OS is about to do the same thing, one level up — creating the illusion of multiple CPUs and private memory spaces.

What Is an Operating System?

▶

A program starts simply — the processor fetches an instruction, decodes it, and executes it, millions or billions of times per second (the Von Neumann model). But while it runs, a whole body of software works to make the system easy to use. That body of software is the operating system.

The OS can be understood from three angles — all three are the same software seen differently:

Virtual Machine — The Illusionist

Takes physical resources (CPU, memory, disk) and transforms them into more general, powerful, easy-to-use virtual forms. This technique is virtualization — the book's central word.

Standard Library — The API Provider

Programs ask for OS features via system calls. Run programs, allocate memory, read/write files. A typical OS exports a few hundred such calls.

Resource Manager — The Referee

CPU, memory, and disk are shared. The OS decides who gets what and when — efficiently and fairly. Many programs, one machine: someone must manage the sharing.

Where the OS sits:

your programs (shell, editor, browser)
        ↕  system call / return
operating system (kernel)
 virtualizes CPU + memory · manages resources
        ↕
hardware — CPU · DRAM · disk · network

A process asks the kernel for service by making a system call; the kernel does the work with full hardware privilege and returns. Programs alternate between user space and kernel space — this boundary IS the OS interface.

System Calls — The OS Interface

▶

xv6 has just 22 system calls. That's the ENTIRE interface between every program and the kernel. Linux has ~350 — same idea, more of them.

// xv6-riscv/kernel/syscall.h (first 10 of 22)
#define SYS_fork    1   // create a new process
#define SYS_exit    2   // terminate this process
#define SYS_wait    3   // wait for a child to finish
#define SYS_pipe    4   // create a pipe
#define SYS_read    5   // read from a file descriptor
#define SYS_kill    6   // send a signal to a process
#define SYS_exec    7   // replace this process with a program
#define SYS_fstat   8   // get file metadata
#define SYS_chdir   9   // change working directory
#define SYS_dup    10   // duplicate a file descriptor

Three functional groups:

  • fork / exec / wait — run programs (processes)
  • read / write / open / close — file I/O
  • pipe — plumbing between programs

A system call is different from a normal function call. A normal call stays in user space — just a jump to another address. A system call crosses the privilege boundary via a trap instruction, switches to kernel mode, does privileged work, then returns to user mode. The crossing has cost — it's not free like a function call.

Mechanism vs. Policy — the split to remember throughout this course:

  • Mechanism = HOW something is done (context switch, page table lookup)
  • Policy = WHICH and WHEN (which process runs next, which page to evict)
  • You can swap the policy without rebuilding the mechanism — this is why they're kept separate

Unix & xv6 — A Short History

▶

Production Line

1969: UNIX at Bell Labs (Thompson & Ritchie). 1975: Sixth Edition spreads to universities (antitrust bars AT&T from selling it). 1977: BSD → lives on in macOS. 1983: System V (commercial). 1991: Linux — written from scratch, Unix-like, wanted a free Unix for PCs.

Teaching Line — Where xv6 Lives

1976: Lions' Commentary — full v6 source annotated line by line. 1979: AT&T bans classroom use of Unix source. 1987: MINIX (Tanenbaum) — small Unix-like OS, no AT&T code, legal to teach. 2006: xv6 — MIT re-implements v6 in modern C for x86. 2019: xv6-riscv — multi-core, runs on RISC-V.

Reading xv6 = reading the 1975 Unix design, in code written to be read. Same architecture and philosophy as v6; rewritten in ANSI C for modern hardware, with real multiprocessor support. MINIX inspired Linux — Linus Torvalds was frustrated by MINIX's limitations and wrote Linux from scratch in 1991.

Meet xv6 — The Kernel We Read All Semester

▶

What It Is

A small, complete, real Unix from MIT. ~6,600 lines of kernel source in C. It boots, runs a shell, runs programs, and has real processes, page tables, and a file system. Small enough to read completely, real enough to be worth reading.

Why Not Just Read Linux?

The Linux kernel is over 30 million lines — nobody learns the core ideas by reading it. xv6 makes the same design choices in a form that fits in your head. Every core concept (processes, memory, files) is visible and traceable.

Two Repos

mit-pdos/xv6-riscv — the clean kernel read in lecture. xv6-labs-2025 — same kernel plus your lab exercises. You boot it in Friday's lab and can change, rebuild, and run it.

The struct proc

Every process in xv6 is one C struct. Fields: state (RUNNING/RUNNABLE/SLEEPING), context (saved registers for switching), pagetable (private memory view), ofile (open files), pid, name. Switching processes = save one context, restore another.

// xv6-riscv/kernel/proc.h — the WHOLE process struct
struct proc {
  struct spinlock lock;
  enum procstate state;    // RUNNING, RUNNABLE, SLEEPING…
  int pid;                 // process ID
  struct proc *parent;     // parent process
  uint64 kstack;           // kernel stack address
  uint64 sz;               // size of process memory (bytes)
  pagetable_t pagetable;   // its private page table
  struct trapframe *trapframe; // saved user registers
  struct context context;  // swtch() here to run process
  struct file *ofile[NOFILE]; // open files
  struct inode *cwd;       // current directory
  char name[16];           // process name (debugging)
};

CPU Virtualization — The Illusion of Many CPUs

▶

Consider a program that simply loops and prints:

// cpu.c — OSTEP Fig. 2.1
int main(int argc, char *argv[]) {
    char *str = argv[1];
    while (1) {
        Spin(1);         // burn CPU for 1 second
        printf("%s\n", str);
    }
}

// One copy running: prints "A" once per second. No surprises.
prompt> ./cpu A
A
A
A  ^C

Now run four copies simultaneously on ONE processor:

prompt> ./cpu A & ./cpu B & ./cpu C & ./cpu D &
A
B
D
C
A
B
D
C
...

All four appear to run at the same time. The hardware can only fetch-decode-execute ONE instruction stream — yet A, B, C, and D all make progress. The OS creates this illusion.

Illusion

Each program believes it has the CPU entirely to itself. Reality: the OS rapidly switches between them.

Mechanism

HOW the switch is done: save this program's registers (its context), restore another program's. (Covered in detail — processes & scheduling weeks.)

Policy

WHICH program runs next and for how long: the scheduler's decision. (MLFQ, proportional share — scheduling weeks.)

Process

A running program — the OS object that owns one of those virtual CPUs. The unit of execution the OS manages.

The order (A B D C instead of A B C D) and the interleaving vary from run to run. On a multi-core machine the pattern changes again. Any interleaving is the correct result — that's the point. The OS gives no guarantees about order, only about progress.

Memory Virtualization — Private Address Spaces

▶ 
// mem.c — OSTEP Fig. 2.3
int main(int argc, char *argv[]) {
    int *p = malloc(sizeof(int));  // allocate one int
    printf("(%d) address of p: %p\n", getpid(), p);
    *p = 0;
    while (1) {
        Spin(1);
        *p = *p + 1;
        printf("(%d) p: %d\n", getpid(), *p);
    }
}

prompt> ./mem & ./mem &
(24113) address of p: 0x200000
(24114) address of p: 0x200000    // SAME address!
(24113) p: 1
(24114) p: 1                       // independent counters!
(24113) p: 2
(24114) p: 2

Both processes claim address 0x200000 — yet their counters never interfere. How?

The OS gives each process a private virtual address space. The OS maps each virtual address to a different physical location in DRAM — programs never see the mapping:

Process A (pid 24113):   virtual 0x200000 → physical 0x51a000
Process B (pid 24114):   virtual 0x200000 → physical 0x77c000

Virtual memory means every process thinks it has the machine's full address space to itself. The OS (with hardware help via the MMU and page tables) silently translates every memory access. Process A reading address 0x200000 and process B reading 0x200000 hit completely different physical RAM. Neither knows the other exists. This is virtualizing memory — covered in depth during the memory weeks.

On modern Linux, the two addresses will likely differ due to ASLR (Address Space Layout Randomization) — address randomization is itself built on this same virtual memory illusion, adding a random offset to every process's layout for security.

The Three Easy Pieces — Course Map

▶

The course follows OSTEP's three-part structure. Each piece answers one core crux: share the machine · coordinate the sharing · make data survive.

Virtualization

CPU: processes, limited direct execution, scheduling (MLFQ, proportional share). Memory: address spaces, paging, TLBs, swapping. The OS as illusionist — making one machine look like many.

Concurrency

Threads and the perils of sharing. Locks, condition variables, semaphores. Concurrency bugs, deadlock, Banker's algorithm. The OS as coordinator — managing threads that share resources.

Persistence

I/O devices and disks. File systems: implementation, FFS, crash consistency, LFS. Distributed systems, NFS, and security. The OS as archivist — making data survive reboots and failures.

The title is a nod to Feynman's Six Easy Pieces — the authors joke that operating systems are about half as hard as physics. The three-part structure isn't arbitrary: virtualization lets us share hardware, concurrency lets shared hardware be used simultaneously, and persistence lets the results of that use survive. Remove any one piece and the OS doesn't work.
