Why Indices Exist

▶

Without an index, finding a record requires reading every block in the file. For 30,000 students in ~1,000 blocks, finding one student = up to 1,000 block reads.

WITHOUT INDEX: find student ID 22201
Read block 1, check all records... not here
Read block 2, check all records... not here
...
Read block 17, found it!   → up to 1,000 block reads

WITH INDEX ON student ID:
Index entry: 22201 → Block 17
Read Block 17 directly      → 2 block reads (index + data)

The index is much smaller than the data file (~8 blocks vs ~1,000). Adding a record does not move any existing records — the index is a separate structure that points into the data file.

An index is a textbook index for your database. The topic is the search key; the page number is the block pointer. The index is read first, then exactly the right block is fetched. 500x fewer reads for a single lookup.

Basic Concepts

▶

Search key: the attribute(s) an index is built on. Different from a primary key — a search key may have duplicate values and one relation can have several indexes with different search keys.

instructor table with three indexes:
  index on ID          ← search key = ID
  index on dept_name   ← search key = dept_name
  index on name        ← search key = name

Composite search key example: (course_id, semester, year)

Two families of index structures:

Ordered Index

Entries stored in sorted order of the search key. Answers both equality (ID = 22222) and range queries (ID between 20000 and 30000). B+-tree is the standard implementation.

Hash Index

A hash function maps each key to a bucket. O(1) equality lookup. Cannot answer range queries at all — there is no order, only hash values.

Five questions to judge any index: lookup speed, range query support, insert cost, delete cost, and space overhead. No single method wins all five.

Ordered Indices

▶

An ordered index stores (search key, pointer) pairs in sorted order. To find a record: binary search the index, follow the pointer, read one block.

SELECT * FROM instructor WHERE ID = 22222;

1. Search index for 22222 → pointer to Block 4
2. Read Block 4
3. Return that one record

Result: 1 of 12 records read (not all 12)

Clustering vs. Non-Clustering

▶

Clustering Index

The physical order of records in the file matches the order of the index. Finding 10 records with dept = 'Physics' fetches one contiguous run of blocks. Only one clustering index per table is possible.

Non-Clustering (Secondary) Index

The file is sorted on a different attribute. The index pointers scatter across many different blocks. Finding 10 records may require up to 10 separate block reads — one seek per record.

Clustering is the most important index property for range queries. A clustering index on dept_name reads one run of blocks for all Physics instructors. A non-clustering index on dept_name may scatter those records across the entire file, requiring a random seek per record — potentially worse than a full scan.

Dense vs. Sparse Indices

▶

Dense Index

One entry per record in the data file. Can answer queries without accessing the data file at all (if the search key is the only attribute needed). Larger — every record has a pointer.

Sparse Index

One entry per block (or per run of records with the same key value). Smaller and cheaper to maintain. Only works with clustering indices — records must be in order so you can scan forward from the nearest entry.

A multilevel index builds a sparse outer index over a dense inner index, reducing search depth. B+-trees generalize this idea into a balanced tree structure.

B+-Tree Index

▶

The B+-tree is the dominant index structure in production databases. It is self-balancing — all leaf nodes are at the same depth regardless of insertions or deletions.

Internal Nodes

Store search keys and pointers to child nodes only. Guide the search down the tree. Typically kept in the buffer pool in memory — few I/Os needed to traverse them.

Leaf Nodes

Store (search key, record pointer) pairs. Linked in a doubly-linked list for efficient range scans. All actual data pointers are in the leaves.

B+-tree properties:
  Height h — typically 2 to 4 for large tables
  Fanout n — up to n-1 keys and n child pointers per node
  All leaves at the same level (balanced)
  Leaves linked: easy to scan from key K1 to K2

Finding one record: h I/Os (tree traversal) + 1 I/O (data block)
For h = 3: 4 total I/Os vs. 1,000 for a full scan

Insertion: find the correct leaf, insert the key. If the leaf is full, split it and push a key up to the parent. Splits propagate up but the tree remains balanced. Deletion: find and remove the entry. If a node is too sparse, merge with a sibling or redistribute keys.

The B+-tree trades a small constant overhead per operation (O(log n)) for eliminating full table scans (O(n)). At a million records, log base 100 of a million is 3 — three internal node reads to find any record. That is why almost every production database uses B+-trees as the primary index structure.

Hash Index

▶

A hash index applies a hash function h(key) to map each search key to a bucket. Equality lookup is O(1) — compute the hash, read the bucket, done.

h(key) = key mod 4

h(12121) = 1  → Bucket 1
h(10101) = 1  → Bucket 1 (same bucket, overflow chain)
h(22222) = 2  → Bucket 2

Equality lookup: compute h(22222) = 2, read Bucket 2 → found
Range query: cannot use hash — there is no ordering between buckets

Static Hashing

Fixed number of buckets. Overflow chains grow as data increases. Performance degrades as chains lengthen. Periodic rebuilding required.

Dynamic Hashing (Extendible)

Bucket count doubles when overflow occurs. A directory of pointers grows with the data. No full rebuild needed — only the overflowing bucket splits.

Hash indices are the right tool for exact-match lookups on a known equality predicate: WHERE ID = 22201. They are completely wrong for range queries (WHERE salary > 80000) or sorted output. Choose B+-tree when in doubt — it handles both equality and range queries well.

Multiple-Key Access

▶

A query with two conditions can use multiple single-column indices or one composite index. The right choice depends on selectivity.

Query: WHERE dept_name = 'Finance' AND salary = 80000

Option A: use dept_name index → fetch matching records, check salary
Option B: use salary index → fetch matching records, check dept_name
Option C: use both, intersect pointer sets → fetch only intersection
Option D: composite index (dept_name, salary) → one index probe, no intersection

Composite index column order matters:

INDEX (dept_name, salary):
  dept_name = 'Finance'           → one contiguous range (good)
  dept_name = 'Finance' AND salary = 80000 → one exact entry (best)
  dept_name = 'Finance' AND salary < 80000 → one range within Finance (good)
  salary = 80000                  → scattered across all departments (bad)

INDEX (salary, dept_name):
  salary = 80000                  → one contiguous range (good)
  dept_name = 'Finance'           → scattered (bad)

The leading attribute is the one you want to range-scan or equality-match.

Using two separate indexes with pointer intersection is only beneficial when both conditions are highly selective. If the dept index returns 2,000 pointers and the salary index returns 1,500, you do 3,500 pointer reads to find 2 answers — a full scan might be cheaper. The composite index avoids this entirely.

Covering Index

▶

A covering index contains all the columns a query needs — the query never touches the data table at all.

Query: SELECT salary FROM instructor WHERE ID = 22222;

Ordinary index on ID:
  3 index page reads → find pointer → 1 random data block read
  Total: 4 I/Os

Covering index on (ID) including salary:
  3 index page reads → salary found in the leaf node itself
  Total: 3 I/Os (data block never read)

At scale, one saved random read per matching row adds up quickly.

Two ways to include a column:

Search Key = (ID, salary)

Salary is part of the sort key. Both ID and salary can be searched. Wider key means fewer entries per node — potentially lower fanout, taller tree.

Search Key = ID, salary INCLUDED

Salary is stored in the leaf but not part of the ordering key. Narrower key preserves higher fanout. Salary can be retrieved but not searched. Usually preferred.

A covering index is query-specific. It carries extra columns so that specific query never has to follow a pointer to the actual table. Adding too many included columns bloats the index and slows inserts. Only add what your most frequent, most performance-sensitive queries actually need.

Index Design Guidelines

▶ 
CREATE INDEX dept_index ON instructor (dept_name);
DROP INDEX dept_index;   -- removes the index, never the data
CREATE UNIQUE INDEX instructor_email_idx ON instructor (email);
  -- unique index = candidate key constraint + access structure
Query PatternBest Index Choice
One selective equality conditionSingle-key index on that attribute
Several AND conditionsCompare: one index + filter vs. intersection vs. composite
Equality on leading attributes, range on trailingOrdered composite index
Query needs only indexed valuesCovering index
Frequent joins on a foreign keyIndex the referencing (child) side
Heavy insert/update/delete trafficFewer indexes — each index costs a write on every DML

Primary keys are indexed automatically by most systems. Foreign keys usually are not. An unindexed foreign key turns every "find the rows that belong to this parent" into a full table scan — and it also slows down DELETE on the parent because the database must verify no orphaned children exist. Index the foreign keys your queries actually use.

The optimizer decides whether to use an index at query time. An index that exists is not always used — if the condition is not selective enough, a full scan is cheaper. Measure before and after, and drop indexes that do not pay for themselves in improved query time.
