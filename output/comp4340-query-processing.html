Three Stages of Query Processing

▶

Every SQL query passes through three stages before returning results:

1. Parse & Translate

SQL is parsed and translated into a relational algebra expression — a tree of operations (select, project, join). Multiple equivalent expressions may exist for the same query.

2. Optimize

The optimizer enumerates execution plans, estimates the cost of each using statistics about the data, and picks the cheapest. The user never sees this step.

3. Evaluate

The evaluation engine executes the chosen plan against the actual data and returns results.

SQL query: SELECT salary FROM instructor WHERE salary < 75000;

Two equivalent algebra expressions:
  A: σ(salary < 75000) → Π(salary) → instructor   (filter first, then project)
  B: Π(salary) → σ(salary < 75000) → instructor   (project first, then filter)

Same answer. But A filters early → fewer tuples to project over → cheaper.

The optimizer's job is to find the lowest-cost plan among all equivalent plans. It doesn't guarantee the globally optimal plan (the search space is too large) but produces a good plan using cost estimates. The user writes declarative SQL — the system decides how to run it.

Measuring Query Cost

▶

I/O cost dominates on magnetic disk. The cost formula counts block transfers and random seeks separately:

Cost = b × tT  +  S × tS

  b  = number of blocks transferred
  S  = number of random seeks (random I/O accesses)
  tT = time to transfer one block
  tS = time for one random seek

Typical values (magnetic disk):   tS = 4 ms,   tT = 0.1 ms
Typical values (SATA SSD):        tS = 90 µs,  tT = 10 µs

Sequential vs. random access — 1,000 blocks:

PatternDisk (ms)SSD (ms)
Sequential (S=1): 1000×0.1 + 1×4104 ms≈10 ms
Random (S=1000): 1000×0.1 + 1000×44,100 ms100 ms

Random access is 39× more expensive than sequential on disk, and 10× on SSD. This single fact drives almost every query optimization decision. Any plan that converts random access into sequential access is likely better, even if it transfers more total data.

Cost models assume B+-tree internal nodes stay in the buffer pool (already in memory). The optimizer discounts the cost of index traversal accordingly — typically only the leaf-level I/O and the data block fetch are counted as "real" I/Os.

Example: find all instructors with salary ≥ 50000
  hi = 3 (B+-tree height), b = 4 (matching blocks), n = 4 (matching records)
  tT = 0.1 ms, tS = 4 ms

A5 (clustering): 3×(0.1+4) + 4 + 4×0.1 = 16.7 ms
A6 (secondary):  (3+4)×(0.1+4)         = 28.7 ms

A5 wins here. But if n is very large, A6 approaches a linear scan cost.

Bitmap index scan — for secondary indices on non-selective conditions: collect all block numbers from the index, build a bitmap (1 bit per block), then do one sequential pass reading only the marked blocks. Avoids repeatedly seeking to the same block.

Conjunctive (AND) selections: use one index and test the other conditions in memory (A7), use a composite index (A8), or intersect pointer sets from two indexes (A9). Disjunctive (OR) selections: union pointer sets from all applicable indexes (A10), or fall back to linear scan if any condition lacks an index.

Join Algorithms

▶

Nested-Loop Join (A1): for each tuple in r, scan all of s. Simple but expensive.

for each tuple tr in r:
    for each tuple ts in s:
        if tr.attr = ts.attr: emit

Worst case: nr × bs + br transfers,  nr + br seeks
Best case (both fit in memory): br + bs transfers, 2 seeks

student (5,000 rows, 100 blocks) JOIN takes (10,000 rows, 400 blocks):
  student outer: 5,000 × 400 + 100 = 2,000,100 transfers → 220 seconds
  takes outer:  10,000 × 100 + 400 = 1,000,400 transfers → 142 seconds
  → smaller outer relation = fewer rescans of inner

Block Nested-Loop Join: pairs of blocks instead of pairs of tuples. s is read once per block of r, not once per tuple of r.

Worst case: br × bs + br transfers,  2×br seeks
student outer: 100 × 400 + 100 = 40,100 transfers (vs 2,000,100)

Indexed Nested-Loop Join: for each tuple in r, use an index on s to find matching tuples. Avoids scanning all of s.

Cost: br(tT + tS) + nr × c    (c = cost of one index lookup on s)
  = 100 + 5,000 × 5 = 25,100 accesses ≈ 103 seconds
  vs. block nested-loop ≈ 4.8 seconds (here BNL wins)

Indexed NLJ is better than BNL when the index is highly selective (few matches per probe). When the inner relation is small or the index is not selective, BNL wins. The optimizer estimates both and picks the cheaper plan based on actual statistics.

Merge Join: both relations must be sorted on the join attribute. Then a single pass aligns them with two forward-moving pointers. If already sorted: br + bs transfers. If not sorted: cost includes sorting both inputs (dominant cost).

student (100 blocks) + takes (400 blocks):
  Already sorted: 100 + 400 = 500 transfers
  Not sorted, M=3: 9,100 transfers + 8,932 seeks

Evaluation Strategies — Materialization vs. Pipelining

▶

Materialization

Each operator writes its full output to a temporary relation before the next operator reads it. Safe and simple. High I/O cost — every intermediate result is written and read back from disk.

Pipelining

Each operator passes tuples one at a time to the next operator without writing to disk. No temporary files. First results reach the user early. Cannot always be used (some operators must see all input before producing output).

Two models for driving a pipeline:

Demand-driven (pull/lazy):
  Parent calls next() on child. Child computes one tuple and returns it.
  open() → next() → next() → ... → close()

Producer-driven (push/eager):
  Each operator runs in its own thread and pushes tuples into a buffer.
  Consumer reads from the buffer. Natural parallelism.

Blocking operators cannot pipeline — they must see all input before producing any output:

  • Sort: run generation phase blocks; merge phase can pipeline
  • Hash join: partition phase blocks; build-probe phase can pipeline
  • Indexed NLJ: waits on its index to be built

Blocking edges split a query plan into pipeline stages. Each stage runs to completion before the next begins. Within a stage, operators pipeline freely.

The double-pipelined join streams both inputs simultaneously. As each tuple arrives from either r or s, it is matched against everything seen so far from the other relation. When memory fills, later tuples spill to disk and are joined in a final pass. This maximizes pipeline overlap when both inputs arrive concurrently.
