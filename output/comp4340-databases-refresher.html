Why Advanced Databases?

▶

A single-disk database works when the DB fits in RAM and one machine handles all queries. As data grows, those assumptions break:

ScaleSituationProblem
Single disk (1–10 TB)DB larger than RAMAccess management and query performance become critical
Multiple disks (10–100 TB)DB doesn't fit on one diskNeed an OS dedicated to storage ops; must still feel like a single disk
Distributed (1+ TB/PB/EB)Global locations, not all holding all dataGlobal location matters; consistency and latency become architectural problems

The goal at every scale: it should feel the same as a single disk to the application. The complexity of distribution, replication, and partitioning is hidden below the query interface. That's the engineering challenge this course is about.

The Database Engine

▶

The database engine has two major subsystems: the Storage Manager and the Query Processor.

Storage Manager — the interface between low-level data on disk and the queries above it:

Authorization & Integrity Manager

Checks constraints and user access rights before any data is touched.

Transaction Manager

Keeps the DB consistent despite failures and concurrent access. Implements ACID properties.

File Manager

Allocates disk space and manages on-disk data structures (pages, extents, segments).

Buffer Manager

Caches disk pages in RAM — allows the DB to exceed RAM size by managing which pages stay in memory and which are evicted.

Storage Manager Data Structures:

  • Data files — store the actual database content
  • Data dictionary — metadata about the schema (table definitions, column types, constraints)
  • Indices — pointers giving fast access to data items without scanning all rows

Query Processor — takes SQL and turns it into execution:

  • DDL Interpreter — interprets DDL (CREATE, ALTER, DROP, TRUNCATE) and updates the data dictionary
  • DML Compiler — translates queries (SELECT, INSERT, DELETE) into evaluation plans; picks the lowest-cost plan (query optimization)
  • Query Evaluation Engine — executes the low-level instructions produced by the DML compiler

Transaction Manager — ACID

▶

Atomicity

A transaction is all-or-nothing. Either every statement in the transaction commits, or none of them do. A crash mid-transaction rolls back all changes already made.

Consistency

A transaction takes the database from one valid state to another valid state. All constraints, rules, and integrity conditions are satisfied after commit.

Isolation

Concurrent transactions execute as if they were serial — each transaction sees a consistent snapshot and doesn't see another transaction's uncommitted intermediate state.

Durability

Once a transaction commits, its effects are permanent — they survive system crashes, power failures, and restarts. Committed data is written to durable storage.

ACID is a promise the database makes to the application. The application can write code assuming these four properties hold, without worrying about concurrent users or hardware failures. The database engine is responsible for keeping that promise — which is most of what chapters 17–19 cover.

Relational Algebra

▶

Relational algebra is the formal language underlying SQL. Every operation takes relations as input and produces a relation as output — so operations can be nested and chained.

Unary:  σ (select)   π (project)   ρ (rename)
Binary: × (product)  ∪ (union)     ∩ (intersect)  − (difference)  ⋈ (join)

σ — Select (keeps rows):

σ dept_name = "Physics" (instructor)
→ returns only rows where dept_name = 'Physics'

Predicates combine with: ∧ (AND)  ∨ (OR)  ¬ (NOT)
σ dept_name = "Physics" ∧ salary > 90000 (instructor)
→ Einstein (95000) survives; Gold (87000) fails the salary test

π — Project (keeps columns):

π ID, name, salary (instructor)
→ drops dept_name column; keeps only the three listed

⚠ Project drops duplicates — a relation is a SET.
π dept_name (instructor) returns 4 rows, not 5,
even if two instructors are in Physics.
SQL tables ARE NOT sets — duplicates survive there.

Composition — operations nest:

π name ( σ dept_name = "Physics" ( instructor ) )
→ σ first: keeps 2 Physics rows
→ π second: extracts just the names
Same as nesting arithmetic — the inner result feeds the outer.

× — Cartesian Product (pairs everything):

instructor × teaches
12 rows × 20 rows = 240 rows
Only 12 of those pairs are meaningful. 228 are noise.
This is why you don't use × directly — use ⋈ instead.

⋈ — Join (NOT a primitive):

r ⋈θ s   =   σθ ( r × s )
Join = build the product, then filter with condition θ.
The product is the expensive part — DBs approach joins differently (hash join, merge join, nested loop join).
⋈ is shorthand that hides this cost.

∪ ∩ − — Set operations:

OperationReturnsCompatibility Requirement
∪ UnionTuples in either or both relationsSame arity + matching attribute types
∩ IntersectionTuples in BOTH relationsSame arity + matching attribute types
− DifferenceTuples in first but NOT in secondSame arity + matching attribute types. Order matters: r−s ≠ s−r

← Assignment and ρ Rename:

← Assignment: stores a result in a temp variable to reuse
phys ← σ dept_name = "Physics" (instructor)

ρ Rename: renames a relation just long enough to finish a query
instructor ⋈ (ρi (instructor))   -- self-join needs two different names

Selection Pushdown — query optimization on day 2: σθ(πL(r)) ≡ πL(σθ(r)) whenever θ only mentions attributes in L. Filter EARLY, carry fewer rows through the rest of the query. This is the central move of query optimization. A select that reduces 10,000 rows to 200 before projecting is vastly cheaper than projecting all 10,000 first.

Joins

▶

A join is a Cartesian product plus a matching condition, said once. These all return the same rows for an inner join:

-- Cartesian product + WHERE (old style):
SELECT name, course_id FROM student, takes
WHERE student.ID = takes.ID;

-- JOIN ... ON (explicit condition):
SELECT name, course_id FROM student
JOIN takes ON student.ID = takes.ID;

-- NATURAL JOIN (matches all shared column names):
SELECT name, course_id FROM student NATURAL JOIN takes;

Natural Join — match on every shared column name:

  • Shared columns appear ONCE in the result (not duplicated)
  • Dangerous: if two tables share more column names than intended, natural join silently over-matches
  • Example: student and course both have dept_name — natural join drops students taking courses outside their own department
  • Fix: use JOIN ... USING (course_id) to name exactly which columns to match on

JOIN ... ON vs. WHERE:

-- ON: matching condition (how rows pair up)
FROM student JOIN takes ON student.ID = takes.ID

-- WHERE: filtering condition (which rows to keep after joining)
-- For inner joins they're equivalent — but for outer joins they differ!

Outer Joins — keep rows with no partner:

LEFT OUTER JOIN

Every row of the LEFT table survives, padded with NULL for unmatched right-side columns. A student with no courses still appears, with NULL course columns.

RIGHT OUTER JOIN

Every row of the RIGHT table survives, padded with NULL for unmatched left-side columns.

FULL OUTER JOIN

Both sides survive. Equivalent to left outer UNION right outer. Unmatched rows from both sides appear with NULLs.

Finding Unmatched Rows

After a left outer join: WHERE course_id IS NULL finds students with no courses — the rows that had no partner on the right side.

Any join TYPE pairs with any join CONDITION. The words "inner" and "outer" are optional — omit them and you get an inner join by default. Matching logic goes in ON; additional filtering goes in WHERE. This separation matters on outer joins where ON and WHERE give different answers.

Indices

▶

Without an index: a query like WHERE dept_name = 'Physics' reads ALL 8 rows and tests each one. With an index on dept_name: read 1 index entry → jump directly to the 2 matching rows. Same answer, 4× fewer reads.

-- Create an index:
CREATE INDEX dept_index ON instructor (dept_name);

-- Search key can be multiple columns:
CREATE INDEX name_dept_index ON instructor (name, dept_name);

-- Unique index (declares the key a candidate key):
CREATE UNIQUE INDEX dept_index ON instructor (dept_name);
-- Fails if duplicates already exist; blocks them going forward.

-- Drop an index:
DROP INDEX dept_index;
-- Name it deliberately — the name is the only handle you have.

Indices are NOT in the SQL standard — the standard covers logical schema only. Indices are physical schema. Widely supported but syntax varies by system. Adding or dropping an index NEVER changes the text of a query — the optimizer decides whether to use it. A wrong answer is never an index problem. A slow answer might be.

What an index costs vs. what it buys:

What You Get

Selective lookups skip the full scan. Primary-key and foreign-key constraint checks get cheap. Updates that find rows by key get cheap too.

What You Pay

Disk space for a second copy of the key data. Every INSERT, DELETE, and UPDATE must also maintain the index. The optimizer may choose not to use it anyway (small table, low-selectivity value → full scan is cheaper).

An index is a speed decision, not a correctness one. Drop every index and every query still returns the right answer — just slowly. Chapter 14 covers B+-tree and hash indices, clustered indices, and how to decide which ones to build.

Transactions

▶

Consider a $100 transfer between accounts — two UPDATE statements that must both succeed or both fail:

UPDATE account SET balance = balance - 100 WHERE number = 'A-101';
-- ← system crashes HERE
UPDATE account SET balance = balance + 100 WHERE number = 'A-215';

-- Without a transaction: A-101 loses $100, A-215 gains nothing.
-- $100 disappears from the total. Neither statement is wrong alone.
-- The PAIR must be all-or-nothing.

A transaction is the unit the database promises to finish completely or not at all.

-- End a transaction:
COMMIT WORK;      -- makes every update permanent; starts a new transaction
ROLLBACK WORK;    -- undoes every update; DB returns to pre-transaction state

COMMIT

All updates become permanent. Survive crashes. Cannot be undone by a rollback. Like saving a document.

ROLLBACK

All updates are erased. DB returns to state before the first statement. Use immediately when a statement reports an error. Like quitting without saving.

Autocommit — the hidden danger:

SystemAutocommit DefaultHow to Group Statements
MySQLONSET autocommit = 0, then COMMIT
PostgreSQLONBEGIN, then COMMIT or ROLLBACK
SQL ServerONBEGIN, then COMMIT or ROLLBACK
OracleOFF for DMLCOMMIT before you disconnect

With autocommit ON, each statement is its own transaction. Two UPDATE statements run as TWO transactions — a crash between them leaves the halfway state committed and permanent. To get atomicity across multiple statements, you must group them yourself with BEGIN / COMMIT. Exit without committing on Oracle and your changes are thrown away. Know your system's default.

Atomicity in practice:

  • If the transaction reaches COMMIT → every effect is kept and survives a crash
  • If it did NOT commit (error, crash, explicit ROLLBACK) → every effect is erased; the DB rolls back on restart
  • Related updates that must stay in sync (e.g., a grade in takes AND the credits in student.tot_cred) belong in one transaction

Chapters 17–19 cover what else transactions guarantee and how rollback is implemented (write-ahead logging, undo/redo).
